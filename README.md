# CoastGuardDatabaseApp

A C# Windows Forms application for managing Coast Guard-themed stations, equipment, personnel, missions, and maintenance records in MySQL.

This is an educational/personal project. It is not an official U.S. Coast Guard application. The included demo data is fictional.

## Features

- Create, view, update, and delete stations, assets, crew members, missions, and maintenance records.
- Associate equipment with stations and missions with equipment.
- Assign multiple crew members to a mission and record each person's role.
- View totals for assets, available equipment, active missions, and equipment with outstanding maintenance due.
- Load records in ascending ID order.
- Use parameterized SQL statements and validate required fields and date ordering.
- Delete missions/crew and their assignments in one transaction when using InnoDB tables.
- Sign in with a basic local administrator login and return to login after logout.

## 1. Open the project

Clone the repository through Visual Studio's **Git > Clone Repository**, then open the solution. A private repository requires access granted by its owner.

Restore NuGet packages from the solution's context menu in Solution Explorer. If any form is linked to a Downloads folder outside the repository, move a copy of its source/designer/resource files into the project and update its project references before building.

## 2. Set up a database

### Fresh demo installation

The included schema is a proposed demo schema inferred from the application. It is not an export of the author's original database or a migration for existing data.

1. Open MySQL Workbench and connect to your local server using an administrator account.
2. Open database/schema.sql and execute it. It creates a NEW database named **coast_guard_assets_demo** with six InnoDB tables.
3. If that database already exists, stop and inspect it first. This script deliberately does not drop or reset databases.
4. Optionally execute database/seed.sql once. Repeating the seed inserts another set of fictional records.

Do not change the supplied schema script to target an existing database containing records you want to keep.

### Existing database

If you already have **coast_guard_assets**, do not run the demo schema against it. Set CG_DB_NAME to coast_guard_assets in step 4 and grant the app account access to that database instead.

Before using an existing schema, verify that:

- All six tables and the columns used by the forms exist.
- Tables participating in deletes use InnoDB, so rollback is supported.
- mission_crew has a primary or unique key on (mission_id, crew_id).
- IDs are generated by AUTO_INCREMENT.
- Foreign keys and deletion policies are intentional.
- Required fields and column lengths match the corrected forms; older incomplete records need completion before updating.

To document the original schema faithfully, export its structure separately in MySQL Workbench using **Server > Data Export > Dump Structure Only**. Review the export for account names/DEFINER clauses and confirm it contains no real data or credentials before committing. Keep it distinct from the proposed demo schema.

## 3. Create a MySQL application account

The application connects as **cg_app**, not root. Use root/another administrator only for database setup.

In a LOCAL, unsaved Workbench query tab, replace CHANGE_THIS_LOCALLY with a new database password and run:

```sql
CREATE USER 'cg_app'@'127.0.0.1'
IDENTIFIED BY 'CHANGE_THIS_LOCALLY';

GRANT SELECT, INSERT, UPDATE, DELETE
ON coast_guard_assets_demo.*
TO 'cg_app'@'127.0.0.1';
```

For the existing database, use **ON coast_guard_assets.*** in the GRANT statement instead. The host portion matches the app's default TCP host, 127.0.0.1. If your local MySQL installation resolves/matches the account as localhost, use that host consistently for the account's CREATE/GRANT/ALTER statements and verify it with CURRENT_USER() after connecting as cg_app.

If that exact account already exists, do not create it again. To intentionally change its password, run locally:

```sql
ALTER USER 'cg_app'@'127.0.0.1'
IDENTIFIED BY 'CHANGE_THIS_LOCALLY';
```

The quoted password must be a valid SQL string literal. If it contains quotes/backslashes, use Workbench's Users and Privileges interface to set it rather than manually escaping it in SQL.

Keep the actual password out of committed SQL, screenshots, source code, and README text. This example must remain a placeholder in the repository. Setting an environment variable does not create or change the MySQL account password.

## 4. Configure Windows user variables

Open Start and search for **Edit environment variables for your account**. Under **User variables**, add or edit these values:

| Variable | Fresh demo value | Purpose |
| --- | --- | --- |
| CG_DB_HOST | 127.0.0.1 | MySQL server |
| CG_DB_PORT | 3306 | MySQL port |
| CG_DB_NAME | coast_guard_assets_demo | Database selected by the app |
| CG_DB_USER | cg_app | MySQL application account |
| CG_DB_PASSWORD | Your cg_app MySQL password | Must match step 3 |
| CG_APP_PASSWORD | A separate password you choose | Password for the app's admin login |

For the original database, use **CG_DB_NAME = coast_guard_assets** instead. If CG_DB_NAME is unset, the corrected code defaults to coast_guard_assets. The database username defaults to cg_app; host and port default to the values above.

CG_DB_PASSWORD and CG_APP_PASSWORD cannot be empty. The app reads Windows **User** variables; setting only a PowerShell session variable or a system-level variable does not satisfy this configuration.

Alternatively, after setting the nonsecret values above, run the contents of scripts/Set-LocalPasswords.ps1 in a local PowerShell window. It prompts for the two passwords without displaying them or embedding them in the script. It does not create a database account or choose the database for you. If running .ps1 files is blocked, use the Windows user-variable dialog instead; no execution-policy change is required.

Restart Visual Studio and the application after setup. User environment variables are local configuration, not an encrypted credential vault.

## 5. Build and log in

1. In Visual Studio, select **Build > Rebuild Solution**.
2. Set CoastGuardDatabaseApp as the startup project if needed.
3. Press F5.
4. Log in with username **admin** and the password you set in **CG_APP_PASSWORD**.

The login username is fixed. There is no registration, password-reset service, or per-user role system. Changing CG_APP_PASSWORD changes this local login password only; it does not change MySQL credentials.

## Basic usage

1. Create a station with a name and location.
2. Create an asset with a name, type, and status. Station assignment is optional.
3. Create crew members with first and last names. Rank and qualification are optional.
4. Create a mission with a type, status, and asset. Dates are optional; enable a date's checkbox to store it.
5. Save the mission, then assign crew and optional roles. Assigning the same person again updates their role when the database unique key is present.
6. Create maintenance records with an asset, type, and status. Dates and notes are optional.

**New** clears the editor. **Save** creates a record. **Update** changes the selected record. Save refuses to insert another record while an existing ID is selected; use New first.

The app displays errors and delete confirmations but no save-success popups. Generated IDs can have gaps after deletion; IDs are identifiers, not row counts.

## Dashboard definitions

- **Total Assets:** every row in asset.
- **Available Assets:** assets whose manually set status is Available.
- **Active Missions:** missions whose status is Active.
- **Maintenance Due:** distinct assets with a next due date today or earlier and a status of Scheduled, In Progress, or Overdue. Completed, Cancelled, and NULL/unknown statuses are excluded. Two qualifying records for one asset count as one asset.

Due dates use the MySQL server's current date. Statuses are entered manually; starting a mission or maintenance record does not automatically change asset status.

## Relationships and deletion behavior

Stations can have many assets. Assets can have many missions and maintenance records. Missions and crew have a many-to-many relationship through mission_crew.

In the proposed demo schema, deleting a station with assets or an asset with mission/maintenance history is blocked. Reassign or remove the related records deliberately first. Deleting a crew member or mission also removes its assignments in one transaction; the underlying other crew/mission records remain.

These deletion rules are confirmed by the supplied demo schema, not by any unreviewed existing database.

## Testing and limitations

Follow [the manual checklist](docs/TESTING.md), including fresh-clone setup, validation, role updates, dashboard counts, persistence, and failed-delete rollback.

The correction package has been reviewed at source level. It has not been compiled or run against MySQL in the preparation environment. Record the Windows, Visual Studio, MySQL, and connector versions used during the first successful end-to-end test.

This is a local desktop CRUD application. It does not implement GPS tracking, automatic scheduling, conflict detection, qualification enforcement, audit logging, or production authentication. Database operations are synchronous and can briefly block the interface. Existing foreign keys, triggers, or different column definitions can change behavior and need separate review.

## Troubleshooting

- **CG_DB_PASSWORD/CG_APP_PASSWORD not set:** create a nonempty User variable under the same Windows account that runs the app.
- **Access denied:** confirm the cg_app password, account host, and grants. The app password and database password serve different purposes.
- **Unknown database:** confirm CG_DB_NAME and run setup only for the intended fresh demo database.
- **Table/column not found:** compare the existing schema with the SQL used by the application.
- **Missing source/designer file:** ensure the project references files inside the repository, not Downloads.
- **Missing MySql.Data assembly:** restore the exact package versions in packages.config and inspect NuGet restore errors.
- **Parent row cannot be deleted:** related records still exist and the database is protecting them.
